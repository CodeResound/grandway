===============================================================================
 PLATFORM TEMPLATE — GUIDE FOR STARTING A NEW PROJECT
===============================================================================

This template is a clean, self-contained starting point:

    .claude governance  +  Django `core` infrastructure  +  Core Policy Engine
    (core.policy_engine)  —  and NO business apps.

Clone it to start a new backend that inherits the same rulebook (.claude/CLAUDE.md),
the same hooks, CI, documentation conventions, and the endpoint/permission registry.
Then build your own apps on top.

Everything below has been verified against this template (215 tests pass on SQLite,
migrate -> sync_policy_registry -> validate_policy_engine --strict passes).

-------------------------------------------------------------------------------
0. WHAT'S IN HERE
-------------------------------------------------------------------------------
.claude/                    CLAUDE.md rulebook, hooks/, settings.json, skills/commands
backend/
  manage.py
  core/
    settings/               base / development / staging / production / testing
    policy_engine/          the standalone registry (models, services, validators,
                            exporters, management commands, docs/)
    nepal/                  bilingual/text/calendar utilities (used by policy_engine)
    docs/templates/         canonical doc templates (API / DATA_CONTRACT / etc.)
    api_urls.py             /api/v1/ router (only `policy/` wired today)
    urls.py                 root urls: admin + health + ready + api/v1
    models.py               BaseModel (UUID pk + created_at/updated_at)
    pagination.py responses.py exceptions.py middleware.py logging.py views.py
requirements/               base / development / production
scripts/ci.sh               lint | export | test | policy stages
.github/workflows/ci.yml     GitHub Actions mirroring the local hooks
pytest.ini  ruff.toml        tooling config
.env  .env.development.example

NOT included (removed on purpose): authenticate, organization, permissions.
The template uses Django's built-in auth.User.

-------------------------------------------------------------------------------
1. PREREQUISITES
-------------------------------------------------------------------------------
- Python 3.12+
- PostgreSQL (only needed for the `policy` CI stage and for real dev/staging/prod;
  the test suite runs on in-memory SQLite with no DB service).
- git

-------------------------------------------------------------------------------
2. START A NEW PROJECT FROM THIS TEMPLATE
-------------------------------------------------------------------------------
a) Copy the folder to your new project location and re-initialize git:

     cp -R platform-template ~/code/my-new-project
     cd ~/code/my-new-project
     rm -rf .git && git init && git add -A && git commit -m "chore: init from platform template"

   (Or: git clone this repo, then point `git remote` at your new remote.)

b) Create the virtualenv and install dev dependencies:

     python -m venv .venv
     source .venv/bin/activate
     pip install -r requirements/development.txt

c) Create your dev env file (values are throwaway dev-only; never commit real secrets):

     cp .env.development.example .env.development
     # edit DB_NAME / DB_USER / DB_PASSWORD / SECRET_KEY as needed
   NOTE: `.env` selects the ENVIRONMENT; `.env.development` holds the dev values
   (see backend/core/settings/development.py). `.env.development` is gitignored.

d) Sanity-check the mechanical gates (no database needed):

     bash scripts/ci.sh lint export test

e) Bring up the database and initialize the policy registry:

     python backend/manage.py migrate
     python backend/manage.py sync_policy_registry
     python backend/manage.py validate_policy_engine --strict
     python backend/manage.py createsuperuser          # for /admin and staff checks

f) Rename cosmetics (optional): search the repo for "platform" / "Platform Template"
   in README.md, .github/workflows/ci.yml (DB names), and .env.development.example
   and replace with your project name.

-------------------------------------------------------------------------------
3. READ THE RULEBOOK FIRST (.claude/CLAUDE.md)
-------------------------------------------------------------------------------
The whole point of this template is that the AI + humans follow one rulebook.
Read the TEMPLATE NOTE at the very top of .claude/CLAUDE.md — it lists the few
sections that reference apps this template does NOT ship, so you adapt them as
you build:

  - Sec 9  (Permissions & Authorization): describes a `permissions` app + a
           check_permission() authority model that are NOT here yet. Until you
           build them, the enforced default is the interim inline pattern:
               if not request.user.is_authenticated: raise NotAuthenticated(...)
               if not request.user.is_staff:        raise PermissionDenied(...)
  - Sec 39 (Nepal Localization): the rules apply if you keep core/nepal/, but the
           "Existing models follow this pattern" list names models not present.
           Delete core/nepal/ AND Sec 39 if your project is not Nepal-specific.
  - Sec 36: references a vision doc (.docs/...) that is not shipped.
  - Sec 35: examples use authenticate.* keys illustratively.

Everything else (Sec 1-8, 10-34, 35 mechanics, 40, doc + /iterations conventions,
and every .claude/hooks/ script) is app-agnostic and applies as written.

-------------------------------------------------------------------------------
4. THE GOLDEN RULE: EVERY ENDPOINT IS REGISTERED IN THE POLICY ENGINE
-------------------------------------------------------------------------------
This is the core discipline the template exists to enforce. No HTTP endpoint may
ship without a matching entry in the Core Policy Engine registry. `validate_policy_engine`
(15 rules) fails CI otherwise, and a hook runs it whenever you edit views/urls/registry.

Full "how to add an endpoint" and "how to remove an endpoint" checklists live in:

     backend/core/policy_engine/docs/INTEGRATION_GUIDE.md

Summary of adding an endpoint:
  1. Declare it in your app's registry.py POLICY_ENDPOINTS (see the schema at
     backend/core/policy_engine/docs/registry_schema.json). Required keys:
     app_key, endpoint_key, permission_key (app.model.action), operation_type,
     display_name — plus route_pattern, http_method, risk_level, category_key,
     and dependencies[] (high/critical risk MUST declare a dependency or set
     is_dependency_root=True).
  2. python backend/manage.py sync_policy_registry     # run immediately after editing registry.py
  3. Regenerate artifacts (see section 6) and stage them.
  4. python backend/manage.py validate_policy_engine --strict   # must pass, 0 findings
  5. Update your app's docs/API.md + docs/DATA_CONTRACT.md.

Removing an endpoint is staged, never a hard delete:
  deprecate_endpoint() -> disable_endpoint() -> (restore_endpoint() to reverse).
  See INTEGRATION_GUIDE.md section 3.

-------------------------------------------------------------------------------
5. ADDING YOUR FIRST APP
-------------------------------------------------------------------------------
Use the `new-app` and `endpoint` skills in .claude/ (they run the compatibility
review + pre-coding gates). Manual outline:

  1. Create the app under backend/<app_name>/ following the layout in CLAUDE.md Sec 2
     (models.py, serializers.py, views.py, urls.py, services.py, selectors.py,
     validators.py, constants.py, exceptions.py, admin.py, tests/, docs/).
  2. Add "<app_name>" to INSTALLED_APPS in backend/core/settings/base.py.
  3. Wire its urls in backend/core/api_urls.py:
         path("<prefix>/", include("<app_name>.urls", namespace="<app_name>")),
  4. Add its endpoints to backend/<app_name>/registry.py POLICY_ENDPOINTS (section 4).
  5. Write DATA_CONTRACT.md BEFORE the models (Sec 5, "No contract = no code").
  6. Business logic in services.py, queries in selectors.py, NEVER in views (Sec 6).
  7. Tests for every endpoint (success/validation/auth/permission/not-found), then run them.
  8. sync_policy_registry -> regenerate artifacts -> validate_policy_engine --strict.

If you need a custom User model, create an `authenticate` (or similar) app with a
User model early and set AUTH_USER_MODEL in base.py BEFORE the first migration.

-------------------------------------------------------------------------------
6. MACHINE-READABLE ARTIFACTS (kept fresh by CI)
-------------------------------------------------------------------------------
backend/core/policy_engine/docs/
  registry_export.json   canonical JSON of every registered endpoint
  openapi.json           OpenAPI 3.1 for the registered surface
  registry_schema.json   JSON Schema contract for one POLICY_ENDPOINTS entry

Regenerate after any registry.py change (and commit them):

  python backend/manage.py export_policy_registry --format registry \
    --output backend/core/policy_engine/docs/registry_export.json
  python backend/manage.py export_policy_registry --format openapi \
    --output backend/core/policy_engine/docs/openapi.json

CI runs `export_policy_registry --check` and FAILS if the committed files drift
from the registry (like makemigrations --check).

-------------------------------------------------------------------------------
7. CONTINUOUS INTEGRATION
-------------------------------------------------------------------------------
scripts/ci.sh is the single source of truth for the gates; CI and developers both
run it. Stages:

  lint    ruff check + ruff format --check           (no DB)
  export  export_policy_registry --check              (no DB)
  test    pytest (core.settings.testing, SQLite)      (no DB)
  policy  migrate -> sync_policy_registry -> validate_policy_engine --strict  (needs Postgres)

Run all locally:    bash scripts/ci.sh
Run a subset:       bash scripts/ci.sh lint export test

.github/workflows/ci.yml runs these on push/PR: a DB-less `lint`+`export` job, a
SQLite `test` job, and a Postgres-backed `policy-engine` job.

The .claude/hooks/ scripts are the same checks fired during an interactive Claude
Code session — CI mirrors them so a commit made outside Claude Code can't bypass them.

-------------------------------------------------------------------------------
8. COMMON COMMANDS
-------------------------------------------------------------------------------
  bash scripts/ci.sh                       # all gates
  pytest                                   # tests (SQLite)
  ruff check backend && ruff format backend
  python backend/manage.py migrate
  python backend/manage.py sync_policy_registry
  python backend/manage.py validate_policy_engine --strict
  python backend/manage.py export_policy_registry --format openapi
  python backend/manage.py runserver

-------------------------------------------------------------------------------
9. GUARDRAILS (from CLAUDE.md — do not violate)
-------------------------------------------------------------------------------
  - No endpoint without a policy_engine registration.
  - No business logic in views; no DB queries outside selectors.py.
  - No schema change without a migration + DATA_CONTRACT update.
  - No new dependency without approval + a THIRD_PARTY_LIBRARIES.md entry.
  - Type hints on all service/selector/serializer signatures; ruff must pass.
  - New branch per work session; never commit to main directly; stage files by name.
  - No completion claim without actually running the tests.
  - Local-first by default: PostgreSQL + local storage, no cloud/hosted infra by default.

Start with .claude/CLAUDE.md and backend/core/policy_engine/docs/INTEGRATION_GUIDE.md.
