# Debug History — Core Policy Engine

## 2026-07-13 — `PolicyEndpointVersion.is_current` could never be flipped (version bumps crashed sync)

**Endpoint/module:** `core.policy_engine.services` (`register_endpoint` update path, `create_version`)
**Problem:** Bumping any endpoint's `version` in a registry declaration made `sync_policy_registry` fail with `PolicyImmutabilityError`. The bug was latent as long as every declaration pinned `1.0.0`; `organization/registry.py` (unit-tree-nodes endpoint) carries a comment deliberately deferring a legitimate version bump because of it.
**Root cause:** `PolicyEndpointVersion` is append-only in both directions — `AppendOnlyQuerySet.update()` raises, and the instance `save()` raises on any non-insert — yet the services called `.filter(endpoint=..., is_current=True).update(is_current=False)` on every version change. The stored `is_current` flag was structurally impossible to maintain: two sources of truth (`endpoint.current_version` and the flag) where one could never be written.
**Changed files:** `models.py` (field removed), `migrations/0004_remove_endpointversion_is_current.py`, `services.py`, `serializers.py`, `selectors.py`, `admin.py`
**Fix summary:** Currency is now derived, never stored: a version record is "current" iff its `version` equals its endpoint's `current_version`. The `is_current` column was dropped (destructive migration, approved 2026-07-13); the API still serializes a computed `is_current`, so the response shape is unchanged. `create_version` now also bumps `endpoint.current_version` — previously it marked a record current without moving the pointer, which under the old model silently disagreed with `endpoint.current_version`.
**Contract impact:** `DATA_CONTRACT.md` 2.0.0 (§6 Currency rule), `API.md` 1.4.0 (§3.3) — non-breaking at the API surface.
**Tests added/updated:** `test_services.EndpointVersionBumpTest` (bump succeeds, appends immutable record, prior record untouched, serializer derives exactly one current), `test_immutability` mutation probes switched from `is_current` to `route_pattern`.
**Notes for future AI:** Never add a mutable state flag to an append-only model — derive state from the owning mutable row instead. The `organization/registry.py` unit-tree-nodes comment deferring its version bump can now be resolved in an organization-app session. This entry also repairs a stale reference: that comment pointed at a `DEBUG_HISTORY.md` entry that was never actually written.

## 2026-07-13 — `_create_version_record` silently reused stale content; `create_version`'s `snapshot` param was ignored

**Endpoint/module:** `core.policy_engine.services._create_version_record`, `create_version`
**Problem:** Two related integrity gaps found during a gap-analysis review. (1) `_create_version_record` used `get_or_create(endpoint=endpoint, version=version, defaults={...})` — if a `(endpoint, version)` row already existed, `get_or_create` silently returned the *existing* row and discarded the newly-passed `http_method`/`route_pattern`/`operation_type`/`view_import_path`, even if they differed from what was stored. Since `PolicyEndpointVersion` is otherwise strictly immutable, this was the one path where content could quietly diverge from what a caller believed it was recording. (2) `create_version()` accepted a `snapshot: dict | None` parameter in its signature but never passed it to `_create_version_record` — the snapshot was always auto-computed, making the parameter dead code.
**Root cause:** `get_or_create`'s `defaults` are only applied on the `created=True` branch — nothing compared the existing row's content against the incoming values on the `created=False` branch. The `snapshot` parameter was added to the public signature without a matching plumbing change to the private helper.
**Changed files:** `services.py` (`_create_version_record`, `create_version`)
**Fix summary:** `_create_version_record` now explicitly checks for an existing `(endpoint, version)` row; if found, it compares `http_method`/`route_pattern`/`operation_type`/`view_import_path` against the incoming values and raises `PolicyVersionConflictError` on any mismatch (reuse is only silent when content is identical — true idempotency, not silent overwrite-by-omission). `create_version()` now threads its `snapshot` argument through to `_create_version_record`, which uses it verbatim when provided instead of always auto-computing.
**Contract impact:** `DATA_CONTRACT.md` 2.1.0 (§6 Integrity rule) — non-breaking; tightens an existing gap rather than changing any external shape. Also added new validation rule 13 to `validate_policy_engine` (current_version ↔ version-record content consistency) as a standing detector for the same class of drift, in case it enters the database through a path other than `_create_version_record` (e.g. a future direct ORM write).
**Tests added/updated:** `VersionSnapshotIntegrityTest` (idempotent same-content reuse, explicit `snapshot` honored, differing-content reuse raises `PolicyVersionConflictError`), `ValidateVersionIntegrityTest` (rule 13: missing version record, content drift).
**Notes for future AI:** `get_or_create` is the wrong primitive whenever "the row already existing" and "the row existing with different content" need different handling — reach for an explicit `.filter().first()` + comparison instead once immutability or idempotency-with-verification matters.

## 2026-07-13 — `register_category()`, `map_endpoint_to_category()`, and `add_dependency()` only partially (or never) reconciled metadata on resync

**Endpoint/module:** `core.policy_engine.services.register_category`, `map_endpoint_to_category`, `add_dependency`, `_update_endpoint_if_changed`
**Problem:** An external review flagged that several registry service functions use `get_or_create()` and only reconcile a handful of fields — or none at all — once the row already exists. Verified directly against the code: `register_category()`'s `elif` branch only compared/updated `display_name` (`description`/`parent`/`icon_key`/`sort_order`/`application`/`policy_model` were frozen at first-creation values); `map_endpoint_to_category()` had no `elif` branch at all — on `created=False` it did nothing, so `display_label`/`help_text`/`sort_order`/`is_visible_in_ui`/`is_sensitive` never updated; `add_dependency()` had the same shape, freezing `enforcement_mode`/`reason`. Verifying also surfaced three unreconciled fields in the already-most-complete `_update_endpoint_if_changed()`: `operation_type` was accepted as a parameter but never checked in `metadata_changed` or ever assigned back to `endpoint.operation_type`; `policy_model` was passed in but never reassigned (re-parenting an endpoint silently no-opped); `is_internal` wasn't even threaded through from `register_endpoint()`.
**Root cause:** The same bug shape repeated four times — `get_or_create(defaults={...})` only applies `defaults` on the `created=True` branch, and nothing compared the existing row's fields against the incoming declared values on the `created=False` branch. `register_application`/`register_model` had already been fixed to reconcile fully (see prior version-bump work); the pattern was never carried over to the category/mapping/dependency functions, and three fields were missed even in the endpoint path that supposedly already did this correctly.
**Changed files:** `services.py` (`register_category`, `map_endpoint_to_category`, `add_dependency`, `_update_endpoint_if_changed`, `register_endpoint`)
**Fix summary:** All four functions now reconcile every mutable field they accept on resync, following the same style already used by `register_application`: direct `!=` comparison for booleans and fields always passed with a real, meaningful value by every current caller (`is_sensitive`, `is_visible_in_ui`, `sort_order`, `enforcement_mode`, `operation_type`, `is_internal`, `policy_model` when provided); truthy/`is not None`-gated comparison for optional string/FK fields where blank/omitted conventionally means "caller didn't specify, don't touch" (`description`, `icon_key`, `help_text`, `reason`, category's `application`/`policy_model`/`parent`). Every reconciling branch logs a changelog entry (`metadata_update` for categories/mappings/dependencies; the existing `metadata_update`/`route_changed`/`method_changed` logic for endpoints). `add_dependency`'s changelog additionally records the before/after `enforcement_mode` in `detail` when it changes, since that field is security-relevant (see Contract impact).
**Contract impact:** `DATA_CONTRACT.md` 2.2.0 — reconciliation rules added to §3 `PolicyEndpoint`, §4 `PermissionCategory`, §5 `EndpointCategoryMap`, §7 `PolicyDependency`. `API.md` 1.8.0 — no HTTP contract change (internal service-layer fix only). The `add_dependency`/`enforcement_mode` gap was a live security concern: the `permissions` app's grant-time dependency enforcement reads `enforcement_mode` to decide whether to block or just log a missing prerequisite, so a `registry.py` declaration tightening a dependency from `warning` to `strict` would previously appear to ship but silently never take effect. Unlike the route/version drift `validate_policy_engine` rules 11–13 already catch, this class of drift was invisible both at write time and at audit time before this fix — no new validation rule was added since most of these fields aren't present in the registry config surface (`lifecycle.py`) at all, so there's nothing independent to diff against; the fix itself closes the gap directly.
**Tests added/updated:** `RegisterCategoryServiceTest`, `MapEndpointToCategoryServiceTest` (new — no prior test coverage existed for either function), plus new cases in `RegisterEndpointServiceTest` (`operation_type`/`policy_model`/`is_internal` reconciliation) and `AddDependencyServiceTest` (`enforcement_mode` tightened/loosened on resync, blank `reason` doesn't wipe an existing one — the security-relevant case has its own explicitly-named test).
**Real-world confirmation:** Running `sync_policy_registry` against the actual dev database with this fix applied surfaced genuine, previously-silent drift — not just a hypothetical: 2 endpoint-category mappings (`authenticate.user.staff_session_revoke` → `user_management`, `organization.organizationmembership.mine_list` → `membership_self_service`) had metadata that no longer matched their current declarations, and 3 dependency rows had a blank/stale `reason` that got reconciled to the registry's declared text. No `enforcement_mode` drift was found on the real data — every currently-registered dependency's enforcement mode already matched its declaration, so the security-relevant case was latent risk, not an active one.
**Notes for future AI:** A `get_or_create()` with an `elif`/no-`elif` update branch is a recurring bug shape in this file — any new registry service function must reconcile every parameter it accepts, not just the ones convenient to check. When adding a new mutable field to any `PolicyApplication`/`PolicyModel`/`PolicyEndpoint`/`PermissionCategory`/`EndpointCategoryMap`/`PolicyDependency`-registering function, immediately ask "does the resync path reconcile this?" — it is not automatic.

**Discovered, not fixed (separate, pre-existing, out of scope for this fix):** the same real-DB sync run showed `register_model()` logging a `metadata_update` changelog entry **twice** for 5 different `permissions`-app models (`role`, `role_permission`, `role_binding`, `grant`, `deny`) on every `sync_policy_registry` invocation — including immediate re-runs with zero registry changes, meaning it isn't idempotent. `register_model()` was not touched by this session's fix (it was already reconciling fully as of an earlier session). Root cause not yet isolated — `model_display_name`/`import_path` declarations for these five models were checked and found consistent across every `permissions/registry.py` endpoint entry referencing them, so the oscillation's exact trigger is still unknown. Flagged for a future `permissions`- or `core.policy_engine`-scoped session; not fixed here to avoid scope creep beyond the category/mapping/dependency/endpoint reconciliation this entry covers.
