# Debug History — Dashboards

## 2026-08-01 — `GET /dashboard/activity/` served the staff-only audit log to Lead Managers

**Endpoint/module:** `dashboards.views.DashboardActivityView`, `dashboards.selectors.get_activity`
**Problem:** A Lead Manager was refused `GET /api/v1/audit/events/` with a 403 and served the same rows by `GET /api/v1/dashboard/activity/` with a 200 — including `action`, `actor_label`, and `summary` for events such as an Admin resetting another account's password. Found by an authorization sweep of all 131 routes against all three authority tiers, not by a test.
**Root cause:** Every other dashboard section is a figure derived from an owning app's selector, which has already applied that app's scoping — so passing the actor down is sufficient. `activity` is the one section that returns another table's rows verbatim, and the `audit` app gates all of its own routes on `is_staff` (`audit/views.py::_require_staff`), which a Lead Manager fails. `get_activity` called `get_events()` with no access check, and `require_dashboard_actor` admits Lead Managers.

The deeper cause is a reasoned-from assumption. `get_activity`'s docstring justified going unnarrowed because scoping "would make this endpoint disagree with `GET /api/v1/audit/events/`, which any of these users may already call" — a premise that was never checked and was false for the one tier it mattered for. The same sentence had propagated into `docs/API.md`, `docs/INTEGRATION.md`, `concepts/dashboards_flows.md`, and **two tests that asserted the leak as intended behaviour** (`test_the_feed_is_not_narrowed_by_authority`, `test_lead_manager_may_read_every_section`). The belief was consistent everywhere; it was just wrong.
**Changed files:** `access.py` (`require_activity_reader`), `views.py` (`DashboardActivityView.resolve`), `selectors.py` (docstring), `docs/API.md`, `docs/INTEGRATION.md`, `../../concepts/dashboards_flows.md`, `tests/test_sections.py`, `tests/test_views.py`
**Fix summary:** `DashboardActivityView` overrides `resolve` to apply `require_activity_reader` — the same `is_staff` rule the audit app applies — after the normal dashboard check. Overriding `resolve` rather than adding the check inside `get` means any verb later added to this view inherits both checks. The rule is restated in `dashboards/access.py` rather than imported, because §4 permits importing another app's selectors and services but not its access checks; both sides now carry a comment saying the other must be kept in step.
**Contract impact:** `API.md` §1.8 and `INTEGRATION.md` — **breaking for a Lead Manager client**, which now receives 403 where it received 200. Documented as a dated change in both, with an instruction to hide the panel rather than let it 403 on load. No response shape changed.
**Tests added/updated:** `test_sections.TestActivityFeed.test_the_feed_is_refused_to_a_lead_manager` (replaces the assertion of equal row counts) and `test_the_feed_is_not_narrowed_for_a_reader_who_may_see_it` (keeps the half of the original property that survives — no per-actor filtering for a permitted reader). `test_views` now excludes activity from the every-section loop and asserts the 403 explicitly.
**Notes for future AI:** A selector that returns another app's rows verbatim inherits that app's access rule; deriving a figure from a scoped selector does not. The distinction is the whole finding. And when a comment justifies an access decision by asserting what some other endpoint permits, verify it against that endpoint's code — here the claim was repeated into four documents and two tests without anyone checking it once.
