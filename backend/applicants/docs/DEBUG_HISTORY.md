# Debug History — Applicants

## 2026-08-17 — Malformed list-filter params returned 500 instead of 400

**Endpoint/module:** `GET /api/v1/applicants/` — `applicants.views.ApplicantListCreateView.get`, `applicants.selectors.filter_applicants`
**Problem:** Any authenticated user sending `?country=not-a-uuid` or `?fiscal_year=garbage` received a 500. The view passed raw `request.query_params` into the selector, where `filter(journeys__target_country_ref_id=...)` raised Django's (non-DRF) `ValidationError` and `fiscal_year_gregorian_range()` raised `ValueError` — neither of which `core.exceptions.global_exception_handler` translates to a 400. Found by the 2026-08-17 pre-production security audit (finding S6, OWASP A04): a cheap error-flood vector and a broken API contract, though no data leaked (the 500 envelope is generic).
**Root cause:** The list endpoint predates the project's filter-serializer pattern; `clients`, `offers`, `institutions`, and `dashboards` all validate query params through a serializer, but the three oldest list endpoints (`applicants`, `leads`, `applicant_journeys`) still read `request.query_params.get(...)` directly.
**Changed files:** `serializers.py` (`ApplicantListFilterSerializer`), `views.py`, `../core/validators.py` (shared `validate_fiscal_year_label`), `docs/API.md`, `tests/test_applicants.py`
**Fix summary:** `ApplicantListFilterSerializer` validates every filter before any query runs — UUID fields as `UUIDField`, enum filters as `ChoiceField`, and `fiscal_year` by round-tripping the actual BS conversion via the shared `core.validators.validate_fiscal_year_label` (so a format-valid but unconvertible `9999/99` is also a 400).
**Contract impact:** `API.md` §1.1 → 1.2.1. Malformed filters now return `400 VALIDATION_ERROR` with field details (previously 500); unknown enum values now 400 instead of returning an empty page. Well-formed but unknown ids still return an empty page and 200.
**Tests added/updated:** `TestApplicantListFilters` — malformed `country` UUID, malformed and out-of-range `fiscal_year`, unknown `status` each assert 400 with the field in `error.details`; a valid `fiscal_year` asserts 200.
**Notes for future AI:** Never pass `request.query_params` into a selector raw — Django's `ValidationError` and `ValueError` from helpers both surface as 500s because the DRF handler only translates DRF exceptions. Copy the filter-serializer pattern (`dashboards/serializers.py`) for every new list endpoint. Also noted during the fix: `fiscal_year_gregorian_range` returns naive `date`s, so `created_at` window edges are UTC-midnight rather than NPT-midnight — a ~5:45 skew at the boundaries, recorded as a future improvement, not fixed here.
