## 7. Flows

**Ship a production-ready version** (replaces the previous prepare-then-hand-over flow)
1. The user says "prepare for production", or runs `/release <N.M.P>`.
2. Preflight: sync; clean tree; the tag does not exist; `dev` contains `main`; every changelog heading has a tag — an untagged heading is published first.
3. Ten-point readiness audit; findings are fixed on the release branch or recorded as deferrals.
4. `release/<N.M.P>` cut from `dev`: version bump, changelog section, `deploy.md` refresh, artifacts, iteration log.
5. Verify: full CI, migration check, three strict validators, production-settings smoke boot including one throttled request.
6. Pull request into `main`, CI watched to green.
   - Red at any point stops the release there; nothing is merged and nothing is tagged.
7. Merge commit into `main`, annotated tag, GitHub Release published with its artifacts.
8. `main` merged back into `dev`; the release URL reported.

**What stays refused** (`git_guard.sh`, unchanged this session)
1. Moving or deleting a tag; deleting a published release; force-pushing.
2. Deleting `main` or `dev`; discarding uncommitted or unpushed work; pointing the checkout at another repository.
   - These hold regardless of instruction, because the recovery for a wrong release is the next PATCH, never a rewrite.

## 8. Gaps
- **The autonomous path has not yet run against a real release.** The command, the rules, and the guard are in place; the first exercise is `v1.0.0` (backfilled onto the commit matching its notes) followed by `v1.1.0` from `dev`.
- The production-settings smoke boot in the verification step needs a reachable Redis for its throttled-request check. Where none is available the check must be reported as skipped, not silently dropped.
- `production.yml` attaches release artifacts only when the release already exists. The command creates the release while the verify jobs run, which is ordinarily enough; if the artifacts job still skips, it is re-run. That timing is a convention, not an enforced sequence.
