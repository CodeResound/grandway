## 7. Flows

**Serve an admin static asset** (corrected)
1. `collectstatic` writes `STATIC_ROOT` through the `staticfiles` backend, which now carries its own `file_permissions_mode` `0644` and `directory_permissions_mode` `0755`.
2. nginx, running as `www-data`, reads the file off the disk through the world bits and returns it at `/static/...`.
   - Previously the backend inherited `FILE_UPLOAD_PERMISSIONS` / `FILE_UPLOAD_DIRECTORY_PERMISSIONS` (`0640`/`0750`) from `FileSystemStorage`, which it subclasses. `www-data` is in neither the owner nor the group, so every asset returned 403 and the admin rendered unstyled with dead JavaScript. The JSON API was unaffected, which is what made it survivable and invisible.

**Store an uploaded document** (unchanged, and verified unchanged)
1. The upload endpoint writes through the `default` backend, which passes no permission options.
2. It therefore still falls back to `FILE_UPLOAD_PERMISSIONS` — `0640` inside `0750` directories, owner and group only, never web-served.
   - Declaring `STORAGES` replaces Django's default dict wholesale, so the `default` entry is restated explicitly; omitting it would have left uploads with no backend. A test asserts both modes directly.

**Upgrade a host that was deployed before `v1.1.1`**
1. Check out the new tag and run the ordinary deploy sequence.
2. Run `chmod -R a+rX /var/www/grandway/static` once.
3. Confirm with `sudo -u www-data test -r /var/www/grandway/static/admin/css/base.css`.
   - Step 2 is not optional and is not covered by step 1: `collectstatic` skips files it considers unmodified, so it never re-applies modes to an existing tree, and `--clear` repairs the files but leaves the already-created directories at `0750`. Both behaviours were tested rather than assumed.

## 8. Gaps
- **Nothing verifies the deployed tree's modes from inside the repository.** The new test runs `collectstatic` into a temporary directory and stats the result, which catches a regression in the settings; it cannot see a host whose tree was written by an older release. That check lives only in `deploy.md` §15 as a `sudo -u www-data test -r` line an operator must run.
- **The nginx configuration is documented in two places** — `deploy/nginx.sample.conf` and the inline copy in `deploy.md` §9. Both were updated together this session by hand; nothing enforces that they stay identical.
- **No test exercises `DEBUG=False` static serving end to end**, because serving static is the reverse proxy's job and no proxy exists in the suite. The failure was therefore reachable only on a real host, and was found by reading the settings rather than by any automated check.
