## 6. Endpoints

### Health — `/health/`
- **Use it when:** confirming a host is alive, and identifying which build it is running — including when its database is unreachable.
- **Methods:**
  - `GET /health/`
- **Send:** none
- **Returns:** `{ status, version }`
- **Notes:**
  - `version` is new in 1.0.0 — an optional added field, so existing clients are unaffected.
  - Now exempt from the production/staging HTTPS redirect, so a plain-HTTP probe returns 200 rather than 301.
- **Errors:** none

### Ready — `/ready/`
- **Use it when:** deciding whether to route traffic to a host.
- **Methods:**

- **Send:** none
- **Returns:** `{ status }` — `ready` (200) or `not ready` (503)
- **Notes:**
  - Response body unchanged this session.
  - Now exempt from the HTTPS redirect, as above.

## 7. Flows

**Deploy a release**
1. Verify no repo-root `.env` is present — a stray one silently selects its own environment.
2. `collectstatic` → `migrate` → `sync_policy_registry` → `validate_policy_engine --strict`.
3. Start the application server.
4. Poll `GET /ready/` until 200, then route traffic.
   - If `/ready/` returns 503, the database is unreachable; `GET /health/` still reports which build is deployed.

**Identify a running build**
1. `GET /health/` → `version` is the deployed application version, equal to the release tag.
   - Answers without touching the database, so it works during a database outage.

## 8. Gaps
- Eight findings were triaged as non-blocking and recorded in `CHANGELOG.md` under `## [Unreleased]` → `### Deferred`, each with the version bump it would require. Chief among them: nothing serves `STATIC_ROOT` from the application, the rotating file log handler is not multiprocess-safe, and there is no dependency lock file.
- `/ready/` checks the database only, not the cache backend — in production the cache is the rate-limit store, so a failed Redis leaves throttling degraded without the readiness probe reporting it.
