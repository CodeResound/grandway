## 7. Flows

**Verify a tag is annotated** (corrected)
1. The release workflow reads `repos/<owner>/<repo>/git/ref/tags/<tag>` and compares the object type.
2. Object type `tag` passes; anything else fails the release.
   - The previous check read `git cat-file -t` in the runner's working copy, where the checkout action leaves the tag ref pointing at the commit the tag peels to. It reported every annotated tag as lightweight.

**Clean up a landed branch** (unchanged in behaviour, changed in mechanism)
1. The merge command carries `--delete-branch`, removing exactly the branch being landed.
2. The repository-wide auto-delete setting stays off.
   - That setting deletes the head branch of every merged pull request and cannot distinguish a task branch from a permanent one. A `dev` to `main` pull request merged under it deleted `dev`.

## 8. Gaps
- **`v1.1.0`'s verification run stays red and cannot be made green** — the workflow that runs for a tag is the one committed at that tag. The corrected check takes effect from the next tag. Disclosed in the changelog; the release's five artifacts were attached directly so consumers lose nothing.
- A workflow step that fires only on a tag has no coverage until a real tag exists. Neither the local suite nor the pull-request CI can exercise the release workflow's tag assertions, so they are first tested in production by definition. A throwaway tag in a scratch repository would close this, and is not set up.
- `main` survived the auto-delete only because GitHub refuses to delete a default branch. No project-level rule protected `dev`; branch protection would have, and it is unavailable on this plan.
