## Leads

## 1. Module

- Name: Leads — enquiry tracking before applicant conversion.
- Base path: `/api/v1/leads/`
- Auth: Bearer access JWT on every endpoint; Admin and Lead Manager only, Superadmin rejected with 403.

## 2. Conventions

- Response: the standard envelope `{ success, message, data, meta }`. Single resources put the object in `data`; lists put an array in `data`.
- Error: `{ success: false, error: { code, message, details }, meta }` — `details` holds field-level problems.
- Auth failures: 401 when unauthenticated (framework-produced, shape not documented here); 403 `LEADS_ACTOR_FORBIDDEN` when the authority type may not perform the action.
- Pagination: `page` and `page_size` params (default 20, max 100); `meta` carries `count`, `page`, `page_size`, `next`, `previous` with absolute URLs or `null`. Applied to the lead list, notes, and history. The two reference-data lists are unpaginated and return `meta` as an empty object.
- IDs: UUID strings.
- Times: ISO 8601 UTC. User-facing datetimes carry a `<field>_bs` sibling holding a Bikram Sambat object; `created_at` and `updated_at` do not.
- List/search/filter/order params:
  - `GET /api/v1/leads/` accepts `stage`, `source`, `search`, `fiscal_year`.
  - `GET /api/v1/leads/sources/` and `GET /api/v1/leads/loss-reasons/` accept `include_inactive`.
  - Ordering is fixed server-side; there is no client-controlled ordering.

## 3. Models

**BsDate** — `{ year, month, day, month_name_en, month_name_np, display_en, display_np }`

- Read-only; appears only as the value of a `<field>_bs` key.

**ReferenceEntry** — `{ id, code, name_np, name_en, name_romanized, requires_detail, is_active, display_order, created_at, updated_at }`

- The shape of both `LeadSource` and `LossReason` — identical.
- `name_romanized` is server-derived and never accepted as input.

**ContactNumber** — `{ id, number, label:[enum], is_primary }`

**StudyInterest** — `{ interested_countries:json, study_level:[enum], field_of_study, preferred_intake, budget_amount?, budget_currency, scholarship_interest, highest_qualification, language_test_status:[enum], interest_notes }`

- `budget_amount` is a decimal string or `null`. Every field is optional.

**UserBrief** — `{ id, username, display_name }`

**Lead (list shape)** — `{ id, full_name_np, full_name_en, full_name_romanized, email, address, source:ReferenceEntry, source_detail, stage:[enum], created_by:UserBrief, contact_numbers:[ContactNumber], last_followed_up_at?, last_followed_up_at_bs?:BsDate, created_at, updated_at }`

**Lead (detail shape)** — the list shape plus `{ study_interest?:StudyInterest, last_followed_up_by?:UserBrief, lost_reason?:ReferenceEntry, lost_detail, lost_at?, lost_at_bs?:BsDate, lost_by?:UserBrief, stage_before_loss, converted_at?, converted_at_bs?:BsDate, converted_by?:UserBrief }`

- Returned by retrieve, create, update, and every lifecycle action. Only the lead list returns the shorter shape.
- The `lost_*` fields populate together and clear together; `converted_at` and `converted_by` are always `null` in this version.

**LeadNote** — `{ id, body, author:UserBrief, created_at }`

**HistoryEntry** — `{ id, action:[enum], actor_type:[enum], actor_id?, actor_label, summary, reason, changes:json, metadata:json, created_at, created_at_bs:BsDate }`

- `changes` maps a field to `{ from, to }` and is empty when the action carried no diff.

## 5. Dependency order

- `Lead` needs `LeadSource` (a lead must be attributed to a source).
- `Lead` needs an authenticated Admin or Lead Manager account (external module: `authenticate`).
- `ContactNumber` needs `Lead` (sent nested in the lead payload).
- `StudyInterest` needs `Lead` (sent nested in the lead payload).
- `LeadNote` needs `Lead`.
- Marking a lead lost needs `LossReason`.
- `HistoryEntry` needs `Lead` and is written only by the server (external module: `audit`).

**Start here:** `LeadSource` — list it to populate the picker, then create the first `Lead`.

## 6. Endpoints

### Lead Source — `/api/v1/leads/sources/`

**Use it when:** populating the source picker on the create-lead form, and on the Admin settings screen.

**Methods:**
- `GET /api/v1/leads/sources/` — list sources (`leads.source.list`)
- `POST /api/v1/leads/sources/` — add a source (`leads.source.create`), Admin only
- `PATCH /api/v1/leads/sources/<source_id>/` — edit or retire (`leads.source.update`), Admin only

**Send (create/update):**
- create: `code`, `name_np`, `name_en`, `requires_detail`, `is_active`, `display_order`
- update: same minus `code`, which is immutable

**Returns:** ReferenceEntry | list[ReferenceEntry]

**Notes:**
- `GET` hides retired entries unless `include_inactive=true` is passed.
- `code` is lowercased on write and must be ASCII.
- `name_romanized` is generated server-side.
- There is no delete; retire with `is_active` set to false.

**Errors:**
- `LEADS_ACTOR_FORBIDDEN` (403) — a Lead Manager attempted a write, or a Superadmin called any method
- `LEADS_SOURCE_CODE_TAKEN` (409) — a source with that code exists
- `LEADS_SOURCE_NOT_FOUND` (404) — no source with that id

### Loss Reason — `/api/v1/leads/loss-reasons/`

**Use it when:** populating the mandatory reason picker on the mark-lost dialog, and on the Admin settings screen.

**Methods:**
- `GET /api/v1/leads/loss-reasons/` — list reasons (`leads.loss_reason.list`)
- `POST /api/v1/leads/loss-reasons/` — add a reason (`leads.loss_reason.create`), Admin only
- `PATCH /api/v1/leads/loss-reasons/<reason_id>/` — edit or retire (`leads.loss_reason.update`), Admin only

**Send (create/update):** identical to Lead Source.

**Returns:** ReferenceEntry | list[ReferenceEntry]

**Notes:**
- Setting `requires_detail` on a catch-all entry forces an explanation when it is chosen.

**Errors:**
- `LEADS_ACTOR_FORBIDDEN` (403) — as above
- `LEADS_LOSS_REASON_CODE_TAKEN` (409) — a reason with that code exists
- `LEADS_LOSS_REASON_NOT_FOUND` (404) — no reason with that id

### Lead — `/api/v1/leads/`

**Use it when:** the lead list screen, the create-lead form, and the lead detail page.

**Methods:**
- `GET /api/v1/leads/` — list leads in scope (`leads.lead.list`)
- `POST /api/v1/leads/` — record a new enquiry (`leads.lead.create`)
- `GET /api/v1/leads/<lead_id>/` — retrieve one lead (`leads.lead.read`)
- `PATCH /api/v1/leads/<lead_id>/` — correct a lead (`leads.lead.update`)

**Send (create/update):**
- create: `full_name_np`, `full_name_en`, `email`, `address`, `source`, `source_detail`, `contact_numbers`, `study_interest`
- update: any subset of the same fields

**Returns:** Lead (detail shape) for create, retrieve, and update; list[Lead (list shape)] for the list

**Notes:**
- An Admin sees every lead; a Lead Manager sees only leads they created.
- A lead outside the caller's scope returns 404, identical to a non-existent one.
- Ownership is set from the token at creation and never moves; there is no assignment or transfer endpoint.
- `stage` is not writable here and is ignored if sent.
- `full_name_romanized` is generated server-side.
- Sending `contact_numbers` replaces the entire set rather than appending.
- Sending `study_interest` upserts the single interest record.
- A new lead always starts at stage `new`.
- `search` matches the Devanagari, English, and romanized names simultaneously.

**Errors:**
- `LEADS_ACTOR_FORBIDDEN` (403) — the caller is a Superadmin
- `LEADS_LEAD_NOT_FOUND` (404) — no such lead, or it belongs to another Lead Manager
- `LEADS_SOURCE_INACTIVE` (400) — the chosen source has been retired
- `LEADS_SOURCE_DETAIL_REQUIRED` (400) — the source requires detail but none was given
- `LEADS_CONTACT_REQUIRED` (400) — no contact number was supplied

### Lead stage change — `/api/v1/leads/<lead_id>/stage/`

**Use it when:** the user picks a new stage from the dropdown on the lead detail page.

**Methods:**
- `POST /api/v1/leads/<lead_id>/stage/` — move to another active stage (`leads.lead.change_stage`)

**Send (create/update):**
- `stage` — required, must be one of the six selectable stages

**Returns:** Lead (detail shape)

**Notes:**
- `lost` and `converted` are rejected here; each has its own action.
- Moving to the stage already held is a no-op and writes no history entry.
- `ready_for_conversion` signals readiness only and does not create an applicant.

**Errors:**
- `LEADS_STAGE_NOT_EDITABLE` (409) — the lead is lost or converted
- `LEADS_STAGE_INVALID_TRANSITION` (400) — a terminal stage was requested

### Lead follow-up — `/api/v1/leads/<lead_id>/follow-up/`

**Use it when:** recording that a manual call or meeting has just happened.

**Methods:**
- `POST /api/v1/leads/<lead_id>/follow-up/` — record a manual follow-up (`leads.lead.record_followup`)

**Send (create/update):**
- `note` — optional; creates a note when non-blank
- `stage` — optional selectable stage
- `followed_up_at` — optional; defaults to now

**Returns:** Lead (detail shape)

**Notes:**
- Grandway does not schedule follow-ups, send reminders, or integrate with phone, email, SMS, chat, or calendar.
- An empty body is valid and records a follow-up at the current time.

**Errors:**
- `LEADS_STAGE_NOT_EDITABLE` (409) — the lead is lost or converted
- `LEADS_STAGE_INVALID_TRANSITION` (400) — a terminal stage was requested

### Lead mark lost — `/api/v1/leads/<lead_id>/lost/`

**Use it when:** the person will not proceed and the enquiry is being closed.

**Methods:**
- `POST /api/v1/leads/<lead_id>/lost/` — close the lead (`leads.lead.mark_lost`)

**Send (create/update):**
- `loss_reason` — required
- `detail` — required when the chosen reason has `requires_detail`

**Returns:** Lead (detail shape)

**Notes:**
- Nothing is deleted; the lead, its notes, and its history all survive and it can be reopened.
- A reason is always mandatory.
- `stage_before_loss` records the stage held immediately before closure.
- The free-text `detail` is stored on the lead but not copied into the history entry.

**Errors:**
- `LEADS_STAGE_NOT_EDITABLE` (409) — already lost or converted
- `LEADS_LOSS_REASON_REQUIRED` (400) — no reason supplied
- `LEADS_LOSS_REASON_INACTIVE` (400) — the chosen reason has been retired
- `LEADS_LOSS_DETAIL_REQUIRED` (400) — the reason requires an explanation but none was given

### Lead reopen — `/api/v1/leads/<lead_id>/reopen/`

**Use it when:** a closed enquiry comes back, or a converted lead needs further lead-side follow-up.

**Methods:**
- `POST /api/v1/leads/<lead_id>/reopen/` — return the lead to active work (`leads.lead.reopen`)

**Send (create/update):**
- `stage` — optional selectable stage; defaults to `follow_up`

**Returns:** Lead (detail shape)

**Notes:**
- The only way back from a terminal stage.
- Clears `lost_reason`, `lost_detail`, `lost_at`, `lost_by`, and `stage_before_loss`.
- Reopening a converted lead does not undo the conversion: `converted_at` and `converted_by` are left untouched so a second applicant can never be created from the lead.
- All previous history is preserved; the reopen is appended.

**Errors:**
- `LEADS_LEAD_NOT_LOST` (409) — the lead is already active
- `LEADS_STAGE_INVALID_TRANSITION` (400) — a terminal stage was requested as the target

### Lead Note — `/api/v1/leads/<lead_id>/notes/`

**Use it when:** the notes panel on the lead detail page.

**Methods:**
- `GET /api/v1/leads/<lead_id>/notes/` — list notes newest first (`leads.note.list`)
- `POST /api/v1/leads/<lead_id>/notes/` — append a note (`leads.note.create`)

**Send (create/update):**
- create: `body`

**Returns:** LeadNote | list[LeadNote]

**Notes:**
- Notes are append-only; there is no edit or delete, and those verbs return 405.
- Notes can be added at any stage, including on a lost or converted lead.
- The note text is not copied into the history entry.

**Errors:**
- `LEADS_LEAD_NOT_FOUND` (404) — no such lead, or it belongs to another Lead Manager

### Lead History — `/api/v1/leads/<lead_id>/history/`

**Use it when:** the activity timeline panel on the lead detail page.

**Methods:**
- `GET /api/v1/leads/<lead_id>/history/` — the lead's chronological history (`leads.lead.list_history`)

**Send (create/update):** none

**Returns:** list[HistoryEntry]

**Notes:**
- Written by the server on every mutation; a client never creates entries.
- Entries are immutable and are never rewritten or removed, including on loss or reopen.
- `changes` is populated only for actions carrying a field-level diff; `summary` is the fallback label.
- Only lead-scoped actions appear; source and loss-reason changes are audited separately.

**Errors:**
- `LEADS_LEAD_NOT_FOUND` (404) — no such lead, or it belongs to another Lead Manager

## 7. Flows

**Record and work a new enquiry**

1. `GET /api/v1/leads/sources/` — capture the chosen source `id`.
   - Empty list: an Admin must configure a source before any lead can be created.
2. `POST /api/v1/leads/` with `full_name_np`, `source`, and at least one contact number — capture the lead `id`. The lead starts at `new`.
   - `LEADS_SOURCE_DETAIL_REQUIRED`: re-submit with `source_detail` filled in.
   - `LEADS_CONTACT_REQUIRED`: at least one contact number is mandatory.
3. `POST /api/v1/leads/<lead_id>/stage/` with stage `contact_attempted` after the first call attempt.
4. `POST /api/v1/leads/<lead_id>/follow-up/` with a note and stage `contacted` once contact succeeds — records the follow-up, adds the note, and moves the stage in one call.
5. `POST /api/v1/leads/<lead_id>/stage/` with stage `ready_for_conversion` when the person is ready. No applicant is created; conversion does not exist in this version.

**Close an enquiry that will not proceed**

1. `GET /api/v1/leads/loss-reasons/` — capture the chosen reason `id`.
2. `POST /api/v1/leads/<lead_id>/lost/` with `loss_reason` and, if required, `detail`.
   - `LEADS_LOSS_DETAIL_REQUIRED`: re-submit with `detail` filled in.
   - `LEADS_STAGE_NOT_EDITABLE`: the lead was already closed; refresh and show current state.
3. `GET /api/v1/leads/<lead_id>/` — the lead now carries the full closed state and remains in the list.

**Revive a closed enquiry**

1. `POST /api/v1/leads/<lead_id>/reopen/` with no body, or with an explicit active stage.
   - `LEADS_LEAD_NOT_LOST`: the lead is already active; no action needed.
2. `GET /api/v1/leads/<lead_id>/` — the loss fields are cleared but any conversion link is unchanged.
3. `GET /api/v1/leads/<lead_id>/history/` — both the original closure and the reopen are present.

**Review a lead's full story**

1. `GET /api/v1/leads/<lead_id>/` — the current state.
2. `GET /api/v1/leads/<lead_id>/history/` — every action, newest first, sourced from the central audit log.
3. `GET /api/v1/leads/<lead_id>/notes/` — the free text. Note bodies live only here, never in history entries, so a complete view needs both calls.

**Configure the pickers**

1. `POST /api/v1/leads/sources/` — capture the new source `id`.
   - `LEADS_ACTOR_FORBIDDEN`: only an Admin may configure.
   - `LEADS_SOURCE_CODE_TAKEN`: the clash may be with a retired entry; list with `include_inactive=true` to check.
2. `POST /api/v1/leads/loss-reasons/` with `requires_detail` set on any catch-all entry.
3. `PATCH /api/v1/leads/sources/<source_id>/` with `is_active` false to retire a channel.

## 8. Gaps

- Conversion does not exist in this version. `stage` `converted` is unreachable through the API, and `converted_at` and `converted_by` are always `null`, because the `applicants` and `applicant_journeys` modules have not been built. A lead stops at `ready_for_conversion`.
- Direct applicant creation, described in `concepts/leads.txt`, has no endpoint anywhere yet.
- The 401 response body shape is produced by the authentication framework and is not documented by this app.
- `LeadSource.code` and `LossReason.code` values vary per installation; codes must never be hardcoded by a client.
- `HistoryEntry.metadata` keys are per-action and not exhaustively specified. Observed keys: `source`, `stage`, `count`, `followed_up_at`, `loss_reason`, `has_detail`, `note_id`, `reopened_from_converted`.
- There are no bulk operations and no lead deletion or archival endpoint.
- An Admin cannot narrow the lead list to one Lead Manager's work; there is no owner filter parameter on `leads.lead.list`.
- The §19.5 blind consumer-contract test was not run for this contract this session.
