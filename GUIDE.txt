===============================================================================
 GRANDWAY — DEPLOYMENT GUIDE (v1.0.0, 2026-08-19)
===============================================================================

 Audience: the engineer or agent deploying this application, working WITHOUT
 access to its source. Everything needed to deploy, operate, back up, and roll
 back is in this file. Where something is undecided or known-imperfect, it is
 stated in §14 rather than omitted.

 Companion files:
   deploy/env.production.example   every variable, annotated
   deploy/gunicorn.conf.py         application server reference config
   deploy/nginx.sample.conf        reverse proxy reference config
   deploy/crontab.sample           scheduled jobs

-------------------------------------------------------------------------------
 1. MODULE
-------------------------------------------------------------------------------

 Entrypoint      core.wsgi:application   (WSGI; an ASGI entrypoint exists at
                                          core.asgi:application but no ASGI
                                          server is pinned and no async views
                                          exist — use WSGI)
 Runtime         Python 3.12
 Framework       Django 5.2 LTS, Django REST Framework 3.16
 API prefix      /api/v1/
 Working dir     The Django project lives under backend/. `core` is importable
                 only from there, so the server must chdir into it:

                     gunicorn --chdir backend \
                              --config deploy/gunicorn.conf.py \
                              core.wsgi:application

 Version at runtime
                 GET /health/ returns {"status":"ok","version":"1.0.0"}.
                 The value comes from the repo-root VERSION file and always
                 equals the release tag. This is how you confirm which build a
                 host is actually running.

-------------------------------------------------------------------------------
 2. RUNTIME REQUIREMENTS
-------------------------------------------------------------------------------

 PostgreSQL 16 — REQUIRED, not a preference.
   The application uses django.contrib.postgres and pg_trgm GIN indexes for
   substring search across nine record types. SQLite cannot run it. The pg_trgm
   extension is created by a migration (leads/0002), so the database user must
   be able to CREATE EXTENSION on first migrate — or a superuser must create it
   in advance:  CREATE EXTENSION IF NOT EXISTS pg_trgm;

 Shared cache — REQUIRED for any multi-worker deployment.
   DRF throttle counters live in the Django cache. With the per-process
   LocMemCache, every rate limit is silently multiplied by the worker count and
   resets on restart. Production settings therefore REFUSE TO BOOT on
   LocMemCache unless THROTTLE_SINGLE_WORKER=true is set as an explicit
   acknowledgement of a one-worker deploy. Redis/Valkey is the expected choice.
   It is a derived store: losing it costs throttle counters and nothing else.

 NOT required — do not provision:
   No message broker. The one scheduled job runs from cron (§9), deliberately
   not Celery. No object storage: file bytes live on a local volume (§4). No
   external/third-party API calls at runtime.

 Dependency caveats (see also §14):
   - There is no lock file and no hashes. requirements/*.txt pins direct
     dependencies exactly, but transitive dependencies resolve fresh at install
     time, so a deploy-day install may not match what CI tested. Build once and
     promote the same artifact rather than reinstalling per environment.
   - base.txt pins psycopg[binary]. psycopg's own documentation recommends
     psycopg[c] or a system build for production; [binary] bundles its own
     libpq. Left as-is for 1.0.0 because changing it requires build tooling in
     whatever image you choose.

-------------------------------------------------------------------------------
 3. CONFIGURATION CONTRACT
-------------------------------------------------------------------------------

 *** THE SINGLE MOST IMPORTANT LINE IN THIS FILE ***

 ENVIRONMENT must be set in the PROCESS environment, not in an env file.

 Environment selection reads ENVIRONMENT before production settings open
 `.env.production`. Setting it only inside that file leaves it unset at the
 moment it is needed, and the process fails closed:

     ImproperlyConfigured: ENVIRONMENT is unset or invalid (got None)

 That failure is correct behaviour — but it is the most common day-one
 deployment failure.

     systemd:  Environment=ENVIRONMENT=production
     docker:   ENV ENVIRONMENT=production   /  -e ENVIRONMENT=production

 *** AND: THERE MUST BE NO `.env` FILE AT THE REPOSITORY ROOT. ***

 The ImproperlyConfigured above only happens when ENVIRONMENT is unset AND no
 repo-root `.env` exists. If one IS present, its value is used instead — and a
 developer's `.env` says ENVIRONMENT=development. A production host in that
 state boots SILENTLY IN DEVELOPMENT MODE: DEBUG=True, no HTTPS redirect, no
 HSTS, no secure-cookie enforcement, and stack traces rendered to clients.
 There is no error and no warning; the only symptom is a working site with
 every protection off.

 `.env` is gitignored, so a `git clone` deployment never has one. A deployment
 that copies a working directory (rsync, scp, docker COPY of the whole tree,
 a VM image built from a developer's checkout) can carry one silently. Verify
 before every deploy:

     test ! -e .env || { echo "REFUSING: stray .env present"; exit 1; }

 This check is step 0 of the deploy sequence in §7.

 Where the rest is read from:
   Production settings read `<repo-root>/.env.production` IF THE FILE EXISTS;
   otherwise the OS environment only. It never falls back to a generic `.env`,
   so a stray development file cannot leak in. A container injecting env vars
   should simply not ship `.env.production`.

 Mandatory — the process refuses to boot without each of these:

   Variable               Read by / purpose
   ---------------------  ------------------------------------------------------
   ENVIRONMENT            Settings selection. Must be exactly "production".
   SECRET_KEY             Django signing AND JWT signing. Rotating it logs every
                          user out — intended after a compromise.
   DB_NAME                PostgreSQL connection.
   DB_USER                PostgreSQL connection.
   DB_PASSWORD            PostgreSQL connection.
   ALLOWED_HOSTS          Bare hostnames, comma-separated, no scheme. Without it
                          every request on the real hostname returns 400.
   CORS_ALLOWED_ORIGINS   Full origins with scheme. The browser origin permitted
                          to call the API and send the refresh cookie. Without
                          it the frontend cannot call the API at all.
   CSRF_TRUSTED_ORIGINS   Full origins with scheme.
   CACHE_BACKEND          Throttle-counter store. See §2.

 Optional — defaults in parentheses:

   DB_HOST (localhost), DB_PORT (5432), DB_CONN_MAX_AGE (60)
   NUM_PROXIES (0) .......... MUST match the real proxy hop count. See §5.
   CACHE_LOCATION (grandway-default)
   THROTTLE_SINGLE_WORKER (false)
   STATIC_ROOT (<repo>/backend/staticfiles) ...... see §4
   MEDIA_ROOT  (<repo>/backend/mediafiles) ....... see §4
   LOG_DIR     (<repo>/logs) ..................... see §4
   AUTH_SESSION_IDLE_HOURS (12), AUTH_SESSION_ABSOLUTE_DAYS (7),
   AUTH_MAX_ACTIVE_DEVICES (3), AUTH_SESSION_LAST_USED_MINUTES (5)
   AXES_FAILURE_LIMIT (5), AXES_COOLOFF_MINUTES (15)
   JWT_ISSUER (grandway), JWT_AUDIENCE (grandway-api)
   OTP_TOTP_ISSUER (Grandway) ... label shown in the operator's authenticator

 First-boot only: SUPERADMIN_USERNAME, SUPERADMIN_EMAIL,
 SUPERADMIN_DISPLAY_NAME. Leave SUPERADMIN_PASSWORD UNSET — see §8.

 Full annotated template: deploy/env.production.example

-------------------------------------------------------------------------------
 4. FILESYSTEM CONTRACT
-------------------------------------------------------------------------------

 Three directories must be writable by the user the application runs as.

 STATIC_ROOT   recommended /var/www/grandway/static
   Written by `collectstatic`. PUBLIC by design — nginx serves it at /static/.
   Nothing in Django serves it with DEBUG=False, so without the proxy block in
   §5 the admin interface renders with no CSS.

 MEDIA_ROOT    recommended /var/lib/grandway/media
   Applicant passports, transcripts, bank statements. Files are written 0o640
   inside 0o750 directories.

   *** DELIBERATELY OUTSIDE ANY WEB ROOT. ***
   Note it is /var/lib/..., NOT /var/www/... . That is not an oversight and it
   is not stylistic. Django guarantees no URL maps to this volume — the only
   path from these bytes to a client is the authenticated endpoint
   GET /api/v1/files/<id>/download/, and a test enforces that no route exists.
   But no test can police your nginx config. Keeping the directory outside the
   web root means a careless `root /var/www/grandway;` cannot reach it even by
   accident. Do not relocate it under the web root, and do not add a media
   location block (§5).

   This is the primary backup target alongside the database (§11).

 LOG_DIR       recommended /var/log/grandway
   Created at settings import — i.e. before the application can report anything.
   If it cannot be created the process exits immediately with
   ImproperlyConfigured naming LOG_DIR. Every worker, every management command,
   and the nightly cron fail identically. A read-only root filesystem or a
   non-root container user is the usual cause.

-------------------------------------------------------------------------------
 5. REVERSE PROXY CONTRACT
-------------------------------------------------------------------------------

 The proxy MUST terminate TLS and MUST set two headers. Reference config:
 deploy/nginx.sample.conf.

 (1) X-Forwarded-Proto — set it, and always overwrite the client's value.

     Django trusts this header to decide whether a request arrived over HTTPS.
     Two failure directions, both severe:

       Forwarding the client's value  -> anyone can declare a plain HTTP
                                         request secure, and every Secure
                                         cookie flag stops meaning anything.
       Not setting it at all         -> every proxied request arrives over
                                         plain HTTP on the loopback, Django
                                         judges them all insecure, and the
                                         HTTPS redirect sends them to a URL
                                         that terminates back at the proxy.
                                         Unconditional redirect loop: the whole
                                         site down on the first request.

 (2) X-Forwarded-For — and NUM_PROXIES must equal the real hop count.

     nginx alone = 1. nginx behind a CDN = 2. This decides which entry is taken
     as the client IP, and it drives BOTH API rate limiting AND login lockout.
     Too high: a client spoofs its own header and evades both. Too low: every
     request looks like the proxy, so one user's failed logins lock out
     everybody.

 Serve:      /static/  from STATIC_ROOT
 NEVER serve MEDIA_ROOT. See the boxed warning in §4 and in the sample config.

 Probes:     /health/ and /ready/ are public, unthrottled, and exempt from the
             application's HTTPS redirect, so a plain-HTTP health check from a
             load balancer returns 200 rather than a 301.

-------------------------------------------------------------------------------
 6. PROCESS MODEL
-------------------------------------------------------------------------------

     gunicorn --chdir backend --config deploy/gunicorn.conf.py core.wsgi:application

 Bind to loopback only; the proxy is the sole thing that should reach it.

 Worker count is coupled to two things:

   CACHE_BACKEND — with LocMemCache every rate limit is multiplied by the
   worker count. Production refuses to boot in that combination unless
   THROTTLE_SINGLE_WORKER=true. Use a shared cache for workers > 1.

   Logging — KNOWN LIMITATION (1.0.0). Django's logging writes a
   RotatingFileHandler under LOG_DIR. That handler is NOT multiprocess-safe.
   With multiple workers — and the nightly cron writing to the same file — a
   10 MB rollover can race: renames overwrite each other and a whole segment
   can be lost, and long lines can interleave. The stdout/stderr stream that
   gunicorn captures is the reliable log source; collect that with journald or
   your container log driver and treat the file as secondary.

-------------------------------------------------------------------------------
 7. DEPLOY SEQUENCE
-------------------------------------------------------------------------------

 Ordered and idempotent — this is EVERY deploy, not just the first.

   0. test ! -e .env        <- see §3: a stray .env silently overrides
                                ENVIRONMENT and can boot production in
                                development mode with DEBUG=True
   1. pip install -r requirements/production.txt
   2. python backend/manage.py collectstatic --noinput
   3. python backend/manage.py migrate --noinput
   4. python backend/manage.py sync_policy_registry
   5. python backend/manage.py validate_policy_engine --strict
   6. start / reload gunicorn
   7. poll GET /ready/ until 200

 Step 4 runs on EVERY deploy, not only the first. The endpoint/permission
 registry is declared in code and synced into the database; skipping it leaves
 the database describing the previous release's endpoints.

 Step 5 is a gate: A NON-ZERO EXIT MUST ABORT THE DEPLOY. It means the shipped
 code and the permission registry disagree, and authorization metadata is not
 something to run inconsistent.

 Step 7: /ready/ opens a database connection. Do not route traffic before it
 returns 200.

 Optional first-deploy seeds (idempotent, safe to re-run):
   python backend/manage.py seed_document_templates --activate
   python backend/manage.py apply_country_checklists

-------------------------------------------------------------------------------
 8. FIRST-BOOT BOOTSTRAP
-------------------------------------------------------------------------------

   python backend/manage.py bootstrap_superadmin

 Leave SUPERADMIN_PASSWORD unset. The command generates a password, PRINTS IT
 ONCE, and flags the account to force a change at first login. Capture that
 output — it is not recoverable.

 *** ADMIN LOCKOUT WARNING — READ BEFORE FIRST LOGIN ***

 The Django admin is OTP-gated: the admin site is replaced with an OTP-enforcing
 one at process start. An account WITHOUT A CONFIRMED TOTP DEVICE CANNOT ENTER
 /admin/ AT ALL — not with a correct password. Enrol the superadmin's
 authenticator immediately after bootstrap, in the same session.

 If you are locked out, these are the recovery levers (all require shell access
 on the host):

   python backend/manage.py reset_superadmin_mfa        # clear the TOTP device
   python backend/manage.py reset_superadmin_password   # reset the password
   python backend/manage.py addstatictoken <username>   # emergency static token

-------------------------------------------------------------------------------
 9. SCHEDULED JOBS
-------------------------------------------------------------------------------

 One job. Reference crontab: deploy/crontab.sample.

   sweep_notifications — nightly (02:15 NPT suggested)

   Raises alerts (checklist due/overdue, missing documents, offer expiry and
   response deadlines, passport expiry, custom reminders) and resolves alerts
   whose condition has cleared.

   Idempotent: every write is a get_or_create against a (recipient, dedupe_key)
   unique constraint. Safe to re-run and safe to run concurrently.

   Needs the full production environment — including ENVIRONMENT in the process
   environment (see §3) and a writable LOG_DIR.

   If it never runs, no notifications are ever raised or resolved. Nothing else
   degrades; the failure is silent from the API's perspective.

   KNOWN LIMITATION (1.0.0): the command exits 0 even when individual alert
   generators fail. It reports failures to stderr but does not signal them, so
   cron's MAILTO will not flag a partially failed night. Capture stdout/stderr
   to a log and monitor it.

-------------------------------------------------------------------------------
 10. HEALTH AND OBSERVABILITY
-------------------------------------------------------------------------------

   GET /health/   Liveness. Does NOT touch the database. Returns 200 with
                  {"status":"ok","version":"1.0.0"} while the process is alive.
                  Use for the process supervisor, and to identify which build a
                  host is running even when its database is unreachable.

   GET /ready/    Readiness. Opens a database connection. 200 {"status":"ready"}
                  or 503 {"status":"not ready"}. USE THIS ONE FOR THE LOAD
                  BALANCER.

 Both are public, unauthenticated, unthrottled, and exempt from the HTTPS
 redirect, so plain-HTTP probes work.

 Logs are structured and machine-readable. Every line carries a request id;
 responses carry it as X-Request-ID, so a user-reported error can be traced to
 its log lines. Passwords, tokens, OTPs, and keys are never logged.

 Note /ready/ checks the database only — not the cache. A failed Redis will not
 be reported by it (see §14).

-------------------------------------------------------------------------------
 11. BACKUP AND RESTORE
-------------------------------------------------------------------------------

 Exactly two sources of truth. Everything else is derived and rebuildable.

   1. The PostgreSQL database
   2. MEDIA_ROOT (the uploaded-file volume)

 Back up both, and back them up together — a database referencing files that
 the media backup does not contain is a broken restore.

 Restore sequence:
   1. restore the database
   2. restore MEDIA_ROOT
   3. python backend/manage.py migrate
   4. python backend/manage.py sync_policy_registry     <- REQUIRED
   5. python backend/manage.py validate_policy_engine --strict

 A restore is NOT complete until step 4 has run: the registry must be re-synced
 from the deployed code, or the database describes whatever endpoints existed
 when the backup was taken.

 The cache needs no backup — it holds only throttle counters.

-------------------------------------------------------------------------------
 12. ROLLBACK
-------------------------------------------------------------------------------

 The rollback unit is a release tag: check out v1.0.0, redeploy, re-run the §7
 sequence.

 HONEST CONSTRAINT: migrations are not automatically reversible. Rolling the
 code back across a migration boundary does NOT roll the schema back. If the
 release you are leaving applied migrations, either
   - reverse them explicitly:  manage.py migrate <app> <previous_number>
     (only if that migration is genuinely reversible — check first), or
   - restore from backup (§11).

 1.0.0 policy: FORWARD-FIX BY DEFAULT. Ship a patch release rather than rolling
 back across a schema change. Release tags are immutable, so v1.0.1 supersedes
 v1.0.0 — v1.0.0 itself is never rewritten.

-------------------------------------------------------------------------------
 13. SECURITY POSTURE — ALREADY ENFORCED, DO NOT UNDO
-------------------------------------------------------------------------------

 Each of these is enforced by the application. Several can be silently defeated
 at the proxy; the list exists so that does not happen by accident.

   DEBUG=False, hardcoded in production settings.
   HTTPS redirect for all traffic, except /health/ and /ready/.
   HSTS: 1 year, includeSubDomains, preload.
        *** preload is a ONE-WAY DOOR for the apex domain. *** Submitting to
        the preload list makes it impractical to serve any subdomain over
        plain HTTP for a long time. Confirm that is intended before submitting.
   Secure + HttpOnly + SameSite=Lax cookies; refresh token is cookie-only in
        production, never in a response body.
   X-Frame-Options: DENY, X-Content-Type-Options: nosniff, XSS filter on.
   CORS is an explicit allow-list with credentials enabled. Never widen it to
        allow-all: with credentials on, that would let any site on the internet
        make authenticated calls with a user's refresh cookie.
   Argon2id password hashing; 12-character minimum.
   django-axes lockout on username+IP (see NUM_PROXIES, §5).
   Django admin is OTP-gated (§8).
   MEDIA_ROOT is never web-served (§4), files 0o640 in 0o750 directories.
   Every mandatory setting fails closed at boot rather than degrading silently.

-------------------------------------------------------------------------------
 14. GAPS — WHAT THIS CONTRACT DOES NOT DECIDE
-------------------------------------------------------------------------------

 Deliberately left to the deployer:
   - Packaging: container vs bare metal vs VM image. Nothing here assumes one.
   - Secret storage and injection. This file states which variables are needed,
     not where they should live.
   - TLS certificate issuance and renewal.
   - The Redis/Valkey instance: provisioning, persistence, and monitoring.
   - Log aggregation and alerting.
   - Backup scheduling, retention, and restore rehearsal.

 Known imperfections in 1.0.0 (all recorded in CHANGELOG.md under Deferred):
   - Static files are not served by the application. If your target has no
     reverse proxy you control, add a static-serving layer (e.g. whitenoise) in
     your own deployment layer.
   - The rotating file log handler is not multiprocess-safe (§6).
   - No dependency lock file or hashes (§2).
   - psycopg[binary] rather than psycopg[c] in production (§2).
   - sweep_notifications exits 0 on partial failure (§9).
   - /ready/ does not check the cache backend, only the database (§10).
   - The application runs on a single node: file storage is a local volume, so
     horizontal scaling across hosts requires shared storage that has not been
     designed or tested.
